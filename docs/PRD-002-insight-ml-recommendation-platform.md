# PRD-002 — ML × 洞悉股票推薦平台

版本：0.1（2026-09-05）  
狀態：規劃中，先自用、後對外開放  
範圍：台股盤後研究、候選股篩選、洞悉解釋、推薦追蹤與 ML 回饋

本文件把 ML 候選、消息／產業／基本面分析、洞悉層與回訓串成一個可追溯的產品。
它不改變現有回測、資料品質或模型部署裁決；實作前仍須為各功能另立任務與 SPEC。

## 1. 產品定位

平台每天回答五個問題：

1. ML 今天選了哪些候選股？
2. 消息、產業和基本面是否支持或反駁原始訊號？
3. 哪些候選值得精讀，哪些只能觀察，哪些應排除？
4. 這些判斷對既有持倉和產業集中度有什麼影響？
5. 以前的推薦後來表現如何，洞悉特徵是否值得回到 ML？

第一版是單一操作者的研究工具。即使只有一個帳號，資料模型仍保留 `owner_id`，讓之後加入多人時不必重做資料隔離。

## 2. 使用者流程

```text
資料更新 → 品質／PIT 閘門 → ML 候選 → 證據包 → 消息／產業／基本面分析
       → 硬性風險篩選 → 精選／觀察／排除 → 發布不可變推薦快照
       → 自選／模擬投組追蹤 → 到期結果 → 第二層 ML 研究與驗證
```

推薦是盤後批次產物，不在使用者開頁時重算。頁面只讀取已發布版本；資料延遲時顯示上一次版本的真實 `as_of` 和延遲原因。

LLM 只能讀取證據包、產生結構化分析與研究假說，不能直接改策略、模型、風控或下單。變更必須進既有回測、purged walk-forward、DSR／研究登記與人工核准流程。

## 3. 推薦分層

平台永遠保存 ML 原始排名，不把 LLM 結論覆蓋成一個新分數。

| 層 | 輸入 | 輸出 | 產品語意 |
|---|---|---|---|
| L0 ML 候選 | 已登記模型的 PIT 特徵與分數 | 全部候選及排名 | 模型認為值得研究 |
| L1 證據分析 | L0 候選＋可得消息／產業／基本面 | 支持、反對、缺口、風險 | 研究摘要，不是交易指令 |
| L2 規則篩選 | L0 分數、L1 結構化欄位、硬性風控 | 精選／觀察／排除 | 可重現的第二層篩選 |
| L3 發布 | L2 結果＋版本與證據 | 不可變推薦快照 | 對外展示的唯一來源 |

第一版的 L2 只使用配置化門檻和明確規則；LLM 的自由文字不能直接決定去留。證據不足的股票進觀察名單，不為了湊數量而進精選名單。

目前分支的 ML Phase 1 尚未取得部署資格，故任何尚未通過適用閘門的模型只能出現在「研究候選」或「模擬觀察」，不能顯示為已驗證推薦。近期回測另有 2023 資料缺口、公司行動未還原、零收盤價等待修問題；受污染的回測結果不得作為推薦證據。

## 4. 證據資料包

每一次候選分析先由程式建立 `evidence_bundle`，再送入 LLM。資料包不是整個資料庫，而是已計算、可引用、帶時間語意的摘要。

```yaml
bundle_id: 2026-09-05-<hash>
as_of: 2026-09-05
available_at: 2026-09-05T20:00:00+08:00
mode: research | paper | live
stock_id: "2330"
strategy_id: ml_net_h20
model_id: <registered-artifact-id>
config_hash: <hash>
data_quality: pass | degraded | fail
sections:
  ml: {}
  events: {}
  industry: {}
  fundamentals: {}
  risk: {}
evidence: []
missing: []
```

每一筆 `evidence` 至少帶 `evidence_id`、來源表或文件、`available_at`、期間、單位、內容雜湊和引用位置。所有時間戳使用 `Asia/Taipei`；低頻資料以公布時間做 PIT 對齊，不以報告期間代替可用時間。

### 4.1 ML 區段

- 模型版本、訓練截止日、特徵清單與 config hash。
- 原始分數、宇宙內排名／分位、預測 horizon、候選產生時間。
- 特徵缺值、模型輸入資料品質、與前一發布版本的排名變化。
- 只能使用樣本外或生產推論分數；訓練內分數不得冒充 OOS 證據。

### 4.2 消息與事件區段

第一版可先接公司公告與法說會；每份文件保存來源 URL、原文雜湊、發布時間、首次取得時間、版本與段落位置。LLM 抽取的欄位可包含事件類型、方向、影響期間、涉及業務和證據引用。

用今天的模型回頭補製多年以前的消息，只能標為研究資料，不可與當時即時生成的資料混為一談；模型可能已看過後續結果，存在前視污染風險。

### 4.3 產業區段

- `stock_meta` 的市場、產業和產業版本。
- 同業和上下游的營收、報酬、成交與事件摘要。
- 產業廣度、產業相對大盤表現、產業共同風險。

產業結論必須區分「整體產業改善」與「單一公司改善」。產業資料缺失時，該區段為 `unknown`，不能由 LLM 推測。

### 4.4 基本面區段

- 月營收與 YoY／MoM、連續成長期間。
- 季度財報：營收、毛利率、營業利益率、現金流、負債與重大變化。
- 估值與資料期間；若沒有可靠的市場預期，不使用「超預期」字樣。

已被 ML 使用的指標不應在 L2 被無條件重複加分；第二層要標示它是新增資訊、變化資訊，還是同一訊號的另一種表達。

## 5. LLM 結構化輸出

每檔股票輸出固定 schema：

```text
analysis_id / bundle_id / model_id / prompt_version
stance: support | neutral | conflict | insufficient_data
supporting_evidence_ids: list[str]
contradicting_evidence_ids: list[str]
event_horizon: short | medium | long | unknown
risks: list[Risk]
missing_data: list[str]
recommended_bucket: select | watch | exclude
rationale: 繁中說明，僅引用 evidence_id
```

LLM 負責整理證據與提出假說；收益、波動、曝險、排名、成本和差異由程式計算。呈現時分開「事實」「推論」「待驗證假說」。數值與引用通過驗證器後才能進報表。

三種結果：

- `select`：通過必要資料和硬性風險規則，且支持證據足夠。
- `watch`：ML 排名值得注意，但有矛盾、資料不足或事件尚未成熟。
- `exclude`：命中明確排除規則；保存排除原因與證據，不刪除候選。

LLM 無法使用、超預算或輸出驗證失敗時，L0 名單和量化理由照常產出，L1 標記缺席；不能阻塞資料、訊號或告警主線。

## 6. 儲存模型

市場真相仍在資料湖，查詢服務層可以使用既有 PostgreSQL。洞悉與推薦寫入 reporting／資料層，不在 `insight/` 純運算模組寫檔。

```text
recommendation_run
  run_id, as_of, strategy_id, model_id, config_hash, status, quality_status
recommendation
  run_id, stock_id, ml_rank, ml_score, bucket, publish_at, bundle_id
recommendation_analysis
  run_id, stock_id, stance, risks, evidence_ids, prompt_version
recommendation_outcome
  run_id, stock_id, horizon, entry_at, exit_at, gross_return, cost, net_excess, drawdown
evidence_bundle / evidence_item
  bundle_id, stock_id, source, available_at, content_hash, payload, version
insight_run
  analysis_id, task, model_id, prompt_version, input_hash, output_hash, usage, status
```

另保存 `watchlists`、`research_notes`、`portfolios`、`transactions` 和 `position_snapshots`。推薦首發快照、人工覆核、交易紀錄和結果不可被後續重算覆蓋。

## 7. 洞悉回饋 ML 的方法

洞悉層留下兩類不同資料：

1. **當時特徵**：事件類型、消息方向、產業狀態、基本面變化、風險標籤、證據完整度、LLM 與 prompt 版本，以及當時的 L0 分數和 L2 分類。
2. **後來結果**：固定 horizon 的成本後報酬、同日基準超額、最大回撤、是否可成交、事件後價格反應和人工覆核結果。

後來結果才是回歸／排名模型的 target；「LLM 說支持」只是 feature 或弱標籤，不能直接當作正報酬答案。被排除與觀察的股票也要有 outcome，否則模型只會學到最後留下來的選擇偏誤。

第一個可行的模型是第二層候選排序器：

```text
target = fixed-horizon cost-adjusted excess return
features = OOS ML score + structured insight features + industry/fundamental features
output = candidate rank / expected return
```

訓練規則：

- 只有 horizon 已成熟、資料完整且可追溯的列才能進訓練；未成熟列保留但 target 為 null。
- L0 分數必須是時間順序的 OOS 推論，不能用訓練內分數餵第二層。
- 使用 purged walk-forward 與 embargo；重疊持有期要在評估中處理。
- 先比較 L0、L0＋固定風險規則、L0＋洞悉特徵三個版本。
- 所有訓練與失敗結果進 `research_log`；新模型先進研究／模擬，不自動替換生產版本。

### 回訓週期

```text
每日：保存候選、證據與當時特徵
到期：補寫 outcome，標記 sample_ready
每月：組裝新資料集、跑固定切分與品質報告
通過後：建立候選 artifact → 研究閘門 → paper 觀察
```

樣本數不能只看股票列數；要同時檢查有效日期數、事件數、不同市場 regime、產業覆蓋和重複事件。以消息建立的歷史樣本，若不是當時即時生成，必須獨立標記。

## 8. 每日流程與失敗行為

1. 擷取資料並依各表 `available_at` 執行品質閘門。
2. 以同一個 PIT 截點計算因子、模型分數和候選宇宙。
3. 建立每檔候選的證據包；任何必要資料缺失時標記，不靜默補零。
4. 送 LLM 產生結構化分析；保存輸入／輸出 hash、用量、版本和失敗原因。
5. 執行配置化硬性篩選、產生精選／觀察／排除。
6. 發布不可變推薦快照，計算相對上一版本的新增、續留、退榜。
7. 更新自選、模擬投組、通知與結果到期清單。
8. 在固定 horizon 到期後計算 outcome，供研究資料集使用。

資料品質 `fail`：不發布新推薦，沿用前一份並顯示原因。LLM `fail`：發布量化結果和「洞悉缺席」標記。推薦生成重跑：相同輸入 hash 不建立重複版本，若資料版本不同則建立新 run。

## 9. 前台資訊架構

自用第一版先做五頁：

| 頁面 | 內容 |
|---|---|
| 今日總覽 | 最新推薦版本、候選變化、資料狀態、重大事件 |
| 選股中心 | L0 排名、L2 分類、支持／反對證據、風險與完整度 |
| 個股研究 | K 線、法人、融資券、營收、因子、消息、產業與 AI 摘要 |
| 自選／模擬 | 觀察原因、筆記、事件提醒、模擬持有結果 |
| 推薦成效 | 原始 ML 與第二層比較、被排除案例、成本後結果 |

每張推薦卡顯示：股票、策略與模型版本、資料截至時間、ML 原始排名、最終分類、支持／反對證據、資料缺口、個人持倉影響和研究週期。不要把分位數顯示成上漲機率；沒有驗證的目標價與停損價不由 LLM 產生。

## 10. 開發分期

| 階段 | 交付 | 依賴與驗收 |
|---|---|---|
| P0 | `recommendation_run`、證據包、不可變快照、資格分類 | PIT、版本、失敗資料可追溯；未驗證模型不能進正式推薦 |
| P1 | L0 選股中心、個股分析、觀察名單與研究筆記 | 可從候選查到所有證據；排除案例保留 |
| P2 | LLM 結構化消息／產業／基本面分析、每日摘要 | schema、引用、缺資料、離線降級與預算閘通過 |
| P3 | outcome 到期計算、推薦成效頁、原始／篩選後對照 | 同一發布時間與成本口徑；不可用未來資料 |
| P4 | 第二層 ML 資料集與固定回訓報告 | OOS L0 分數、purged walk-forward、成熟 target、研究登記 |
| P5 | 提案、paper 觀察與模型版本晉級 | 既有研究閘門、人工核准、失敗結果保留 |
| P6 | 多使用者、通知、訂閱與對外服務 | 權限隔離、資料／行情授權、法遵審查與容量測試 |

第一個工程切片應是 P0：先讓每天的 ML 候選、分析輸入和發布結果全部可重播，再接 LLM。這能避免先做漂亮頁面，卻沒有足夠資料回頭驗證第二層是否真的增加價值。

## 11. 目前分支的執行邊界

- T-149／T-150 的 2023 因子重物化與 broker 讀取效能修正完成前，不以缺口期間結果訓練第二層。
- T-151 的公司行動、分割／減資和零收盤價問題完成並重新驗證前，不把受影響的大盤比較放入推薦成效基準。
- D-066 的 ML 重訓是乾淨基準與證偽測試，不是調優；第二層洞悉模型不可用來繞過該裁決。
- LLM 的新聞／法說特徵是新研究路線，需另立資料來源、PIT、成本和驗收規格。
- 服務層 API 保持唯讀；任何策略或模型變更仍由 CLI／研究流程和人工核准負責。

## 12. 成功指標

先看平台是否可靠，再看投資結果：

- 100% 推薦列可追溯到模型、資料版本與證據包。
- 資料或 LLM 失敗時，基本流程不產生虛構結果、不阻塞主線。
- 推薦結果能重建，重跑不重複發布。
- 每個到期候選都有 outcome，包含排除與觀察案例。
- L0、固定規則和 L2 模型能在相同期間、宇宙、成本和 horizon 下比較。
- 只有通過既定研究閘門和 paper 觀察的策略才可成為正式推薦來源。

平台最終要證明的不是「LLM 講得像分析師」，而是加入洞悉資料後，推薦在樣本外、成本後和可執行限制下，是否比原始 ML 更有用。
