# LOOP — 三大閉環

系統的品質不靠一次做對，靠三個會自我修正的迴圈。每個迴圈都有：輸入、閘門（gate）、
產出物（artifact）、回饋路徑。閘門條件全部是可機器判定的，不依賴主觀判斷。

## 1. 研究閉環（策略/因子的生命週期）

```
想法 → 因子規格 → 單因子檢驗 → 組合回測 → 審查閘門 → 模擬倉 → 小資金實盤 → 歸因
  ▲                                                                        │
  └────────────── 歸因結果、失效偵測、新資料 ──────────────────────────────┘
```

| 階段 | 閘門條件（全過才晉級） | 產出物 |
|---|---|---|
| 因子規格 | 寫成 `docs/factors/<name>.md`：假說、公式、資料需求、預期方向 | 因子規格文件 |
| 單因子檢驗 | RankIC 均值 t-stat ≥ 2；IC 衰退半衰期 ≥ 持有週期；與既有因子庫相關 ≤ 0.7 | IC 報告（自動生成） |
| 組合回測 | 成本後 Sharpe ≥ 1.0；MDD ≤ 25%；年周轉 ≤ 配置上限；deflated Sharpe p < 0.05（計入嘗試次數） | 回測報告 |
| 審查閘門 | walk-forward 樣本外 Sharpe ≥ 樣本內 50%；參數 plateau 檢查（鄰域參數 Sharpe 差 < 30%） | 驗證報告 |
| 模擬倉 | ≥ 60 個交易日；實際-模擬追蹤誤差年化 ≤ 3%；成交假設誤差（滑價實際/預估）≤ 1.5 倍 | 模擬對帳報告 |
| 小資金實盤 | ≥ 60 個交易日；績效落在回測分布的 [5%, 95%] 信賴帶內 | 實盤歸因報告 |

**嘗試次數登記**：每一次「跑過回測的參數組合」都要記錄在 `research_log.parquet`
（策略、參數 hash、日期、Sharpe）。deflated Sharpe 的 trials 數從這裡來，
禁止洗掉重來。這是防止過擬合的核心機制。

**降級規則（回饋路徑）**：實盤策略連續 3 個月績效落出信賴帶下緣，或 20 日追蹤
誤差超標 → 自動降回模擬倉狀態並告警；因子 RankIC 滾動 12 個月 t-stat < 1 → 標記
「疑似失效」，進下一次研究週期重新檢驗。

## 2. 開發閉環（AI 實作的品質迴圈）

定義在 [CLAUDE.md](../CLAUDE.md) §2。要點：

- 任務佇列（TASKS.md）→ 規格（SPEC 驗收條件）→ 測試先行 → 實作 →
  機器閘門（`python -m twquant check`）→ 完成定義自查 → 收尾
- 閘門是強制的、自動的、不可協商的。弱模型寫出的錯會被測試與型別攔住，
  而不是靠模型自覺。
- 卡住三輪 → DECISIONS.md 待裁決 → 換任務。人（或高階模型）只處理裁決，
  不處理日常實作。

規格的撰寫規則（讓任何模型可實作）：
1. 每條驗收條件（AC）必須是可寫成測試的具體陳述，含輸入、輸出、精確度
2. 介面用 Protocol/型別簽名寫死，不用散文描述
3. 每份 SPEC 有「範圍外」段落，明確說不做什麼
4. 範例輸入輸出直接放在 SPEC 裡（doctest 風格）

## 3. 營運閉環（每日生產迴圈）

```
16:30 資料擷取 → 17:30 品質閘門 → 18:00 因子/訊號 → 18:30 次日目標權重
  → 08:30 盤前檢查 → 09:00- 執行 → 14:00 對帳 → 17:00 歸因與漂移偵測
  → 告警/自動降風險 → （回饋）調整明日風險預算
```

| 步驟 | 閘門/規則 | 失敗行為 |
|---|---|---|
| 資料擷取 | 每來源有預期表清單與最小列數 | 重試 3 次（指數退避）→ 告警，pipeline 標記 degraded |
| 品質閘門 | schema 驗證；跨來源交叉核對（如三大法人合計 vs 個股加總誤差 ≤ 0.5%）；缺漏股票數 ≤ 0.5% | 不過 → 當日不產生新訊號，沿用前日權重並告警 |
| 訊號生成 | 因子值分布與 60 日歷史比對，PSI > 0.25 告警 | 異常因子當日權重歸零 |
| 盤前檢查 | 帳戶現金/持倉與系統帳一致；當日處置股清單過濾 | 不一致 → 禁止下單，人工介入 |
| 執行 | 單股參與率 ≤ ADV 5%；漲跌停不追單；分批 TWAP | 未成交部分記錄，不隔日追 |
| 對帳 | 券商回報 vs 系統預期逐筆對 | 差異 → 凍結新單 + 告警 |
| 漂移偵測 | 同日「PaperBroker 模擬損益 vs 實盤損益」差異滾動 20 日年化 ≤ 3% | 超標 → 部位縮至 50%，連 5 日超標 → 全平倉待裁決 |

**kill-switch（最外層保險，任何時候優先）**：
- 單日虧損 > 帳戶淨值 3% → 停止開新倉
- 回撤自高點 > 15% → 全部策略降至 50% 風險預算
- 回撤 > 20% → 清倉、停機、等待人工裁決
- 資料品質閘門連續 3 日不過 → 停機

閾值全部在 `configs/risk.yaml`，此處數字為初始值。

## 4. 洞悉閉環（LLM 提案迴圈，SPEC-008）

```
營運/研究閉環的產出物（歸因、漂移、因子健康度、research_log）
  → LLM advisor（週頻）產生結構化提案 → proposals/ (pending)
  → 自動回測驗證（走 §1 研究閉環的同一套閘門）→ validated | rejected_by_gate
  → 人工核准（CLI）→ 模擬倉 60 日 → promoted | demoted
       │
       └── rejected/demoted 的提案與原因回饋進下次 advisor 輸入（不重提測過的東西）
```

規則：
- LLM 永遠只能提案，不能執行；提案不繞過 §1 的任何閘門
- `no_action` 是合法且預設的提案結果——沒有值得改的就不改
- 提案的嘗試次數同樣計入 research_log（deflated Sharpe 的 trials 包含 LLM 提的）
- 模型路由與預算見 MODEL-POLICY.md §3

## 5. 四個閉環的關係

開發閉環保證「程式碼做的是規格說的」；研究閉環保證「規格說的在統計上值得做」；
營運閉環保證「實盤發生的與研究預期一致，不一致就自動收手」；
洞悉閉環讓系統「自己讀自己的報表、自己提出下一輪假說」，但提案仍受研究閉環
的機器閘門與人工核准約束。任何一環的產出物（IC 報告、閘門日誌、歸因報告、
提案紀錄）都是下一輪迭代的輸入——系統的改進不需要任何人記得任何事，
全部由 artifact 驅動。
