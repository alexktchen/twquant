## 3. 推翻前一份交接的一個結論

前一份說「訊號是真的，只是被成本吃掉」。**在乾淨資料上對照四個公開因子後，這個框架不成立**：

| | ML（L0-new） | 四因子（X1） |
|---|---|---|
| **0× 成本 CAGR** | +18.21% | +16.97% |
| 1× 成本 CAGR | +13.65% | +12.36% |
| **成本拖累／年** | **4.56%** | **4.61%** |
| 周轉 | 949% | 618% |

**成本設成 0，ML 對四個公開因子只贏 +1.24pp、月度區塊 t +0.33。** 且兩者的成本拖累幾乎相同
（4.56% vs 4.61%），儘管 ML 周轉高 53%。**不是成本吃掉訊號，是訊號本來就這麼薄。**
「降頻 + EMA」那條路的前提被證偽。

## 6. 目前的問題（按嚴重度）

### 6.1 沒有任何資金水位在測「持有恰好 N 檔」

| | 設定 | 10M 實際 | 80M 實際 | 80M 參與率擋單 |

80M 下賣單被 ADV 5% 參與率上限擋住，部位殘留；10M 下買不起一張。
**階梯的「20 檔 vs 40 檔」比較，實際上是在比 32 檔 vs 45 檔。** 未解決。

### 6.2 稀疏閘門相乘會歸零（D-076）

M2／M3 曝險 **3%**、GALL 曝險 **0%**——判定機械套用會得出結論，但那是空殼之間的比較。
根因是稀疏事件（`flag_hold_50d` 每日 0~5 檔）乘上任何 30% 的池子，交集期望值 0~1.5 檔。
**已修**：MG 基座由 M2 改為 M1。**未修**：`scripts/` 還缺一個「配置可行性預檢」，
應對候選配置抽樣數個訊號日、回報通過全部濾網的檔數中位數，低於 top_n 一半即警告。

### 6.3 DSR 試驗計數已達 87 次

D-071（18）＋ D-072（21）＋ D-073（21）＋ D-074（3）＋ D-075（3）疊在原有 21 次之上。
**87 次試驗下，DSR 要求的 Sharpe 門檻遠高於單次測試**——這是「不得挑冠軍」的量化理由，
不是保守。任一格要晉升須另立事前登記、獨立重跑，並承擔已消耗的計數。

### 6.4 broker 因子每天全撈整表（T-150）

`chip.broker_*` 每天無條件全撈 `broker_trades`（5,700 萬列、單次 286 秒），
使全因子物化慢到 90 分鐘／天、峰值記憶體 20.6 GB。**未修**。
T-083 已對 `prices_daily` 做過同一件事（`since` 推進 SQL，100 → 3.8 秒/日）。

### 6.5 2021 年有 727 列 `close = 0`

其中 218 列 `volume > 0`（有成交卻沒收盤價，資料自相矛盾）。標籤路徑的 `>0` 防護擋得住，
但因子與報表未必。已做成 `audit_silent.py` 的檢查 #10，**未修**。

## 9. 明確不要做的

- **不要挑冠軍**。87 次試驗下，最好那格的 Sharpe 有很大一部分是選擇偏誤。
- **不要為了讓某格好看而改事前登記的門檻**——那正是登記要防的。
- **不要重啟 ML 的特徵工程或調參**（D-066 乙層明文禁止）。改投組建構是架構，允許。
- **不要在事件型閘門上再疊閘門**，除非先算過交集大小（D-076）。
