# autotrade — 獨立的程式交易系統（規格）

裁決：`DECISIONS.md` D-222 與其修訂（2026-11-12）。
使用者要一套**獨立且完整**的程式交易系統，不跟線上的 twquant 放一起。

## 1. 邊界

- 這個資料夾自成一套：自己的 `pyproject.toml`、設定、測試、閘門。
- **不 import `twquant`**，不讀 twquant 的設定與資料庫。twquant 的閘門也不檢查這裡。
- 跟 twquant 的接點有兩個：**單向輸出**（§3 的 `export`，把狀態寫給網站讀），以及 2026-11-13 起多的一條
  **回程**（§3 的 `control`）：D-225 起網站可以要求緊急停止；D-229（2026-11-14，使用者要求）起還可以平倉、
  暫停／恢復自動交易、啟動／結束交易程式。仍然不能從網站做的：手動買賣、改設定、解除緊急停止。
  twquant、網站或資料庫壞了、連不上，交易照跑（讀不到指令不算錯，但要記下來）。
- 核心只用 Python 標準函式庫（元大行情元件是 32 位元，執行環境越單純越好）。
  只有元大轉接器用 `comtypes`，只有輸出與中繼程式用資料庫套件。**交易程式那個程序不連資料庫**：
  要給雲端的寫成本機檔案，要從雲端拿的由中繼程式（另一支程序）寫成本機檔案（A-011）。
- 沿用 repo 的黃金規則：時間一律 tz-aware `Asia/Taipei`；不准靜默處理；參數放設定檔；
  秘密只放 `.env`。

## 2. 第一個上線目標

動能順勢（網友原版 Momentum_Scalping，只做多）、微台 1 口、行情與下單都走元大期貨。

## 4. 驗收條件

### A-001 帳務與風控

- **AC1 帳務**：買進再賣出後部位為 0；已實現損益＝（賣價−買價）×每點價值×口數−兩邊成本；
  成本＝手續費＋期交稅（成交價×每點價值×稅率，四捨五入到元）。
- **AC2 對帳**：帳上部位與券商回報的部位不同時 `reconcile` raise，訊息含兩邊的數字。
- **AC3 部位上限**：任何會讓部位超過 `max_position` 或低於 `min_position` 的委託被拒絕。
  不變量：照風控放行的委託全部成交後，部位永遠在上下限之內（屬性測試）。
- **AC4 每日虧損上限**：已實現＋未實現損益 ≤ −上限時進入停手；停手後拒絕新倉。
- **AC5 平倉永遠放行**：停手、超過進場次數、過了進場時段、行情過舊時，
  只會減少部位的委託仍然放行。唯一例外是「暫停送單」（A-010 AC1、AC5）。
- **AC6 進場時段與次數**：進場時段外、或當日進場次數已達上限，拒絕新倉。
- **AC7 行情過舊**：最後一筆行情距今超過 `max_quote_age_s`，拒絕新倉。
- **AC8 真單設定**：`mode = "live"` 而每日虧損上限沒設定時，讀設定就 raise。
- **AC9 時區**：任何 naive datetime 進到帳務或風控就 raise。
- **AC10 換日**：交易日一換，進場次數、當日損益、因每日上限造成的停手歸零；
  人工緊急停止不會自動解除。

### A-002 模擬券商、委託管理、重播行情、主引擎

- **AC1 模擬成交**：市價單在送出後滿 `sim.latency_s` 的第一筆行情成交，價格＝該筆成交價 ± `sim.slippage_points`；
  限價單只在行情穿過限價時以限價成交；刪單在下一筆行情生效。
- **AC2 委託狀態機**：不認得的委託編號、已結束的委託又收到回報、成交口數超過委託、
  成交的買賣別或商品跟委託不同，一律 raise；部分成交後委託仍算活著。
- **AC3 在途委託算進部位**：風控看的是「實際部位＋還沒成交的委託」。
  不變量：隨機送單下，實際部位永遠在上下限內，且帳上部位等於券商部位（屬性測試）。
- **AC4 停手即平倉**：碰到每日虧損上限時，刪掉還沒成交的新倉單、市價平倉，之後的新倉被拒絕。
- **AC5 強制平倉時間**：過了 `risk.force_flat_time` 還有部位，由系統市價平倉（策略自己沒平掉時的最後防線）。
- **AC6 委託逾時**：新倉單超過 `risk.order_timeout_s` 沒成交就刪單；
  **平倉單逾時視為券商或連線異常**：刪單、緊急停止，刪單回報後重送市價平倉。
- **AC7 收盤確認與對帳**：每次成交後跟券商部位對帳，不一致就修正並停手（2026-11-13 起，見 A-010 AC6；原本是 raise）；
  收盤時還有部位或還有活著的委託，`finish` raise。
- **AC8 重播行情**：讀期交所每日逐筆檔，取成交量最大的到期月份，排除價差單、別的商品、別的日子、時段外；
  同一秒內每筆加 1 微秒；欄位不足或價量讀不懂就 raise（含檔名與列號）；找不到資料就 raise。
- **AC9 決定性**：同一份行情與同一個策略跑兩次，事件與損益完全相同。
- **AC10 緊急停止**：`Engine.kill` 平倉並停手；換日後仍然停手。
- **AC11 指令列**：`python -m autotrade replay` 用模擬券商重播一天並印出摘要；`check-config` 驗證設定檔。

### A-003 事件日誌與狀態還原

- **AC1 只增不改**：每筆一列 JSON，帶序號、時間、種類、內容、前一筆的雜湊與自己的雜湊；
  每筆寫完就 flush 並 fsync；重新開檔會先驗證既有內容再接著寫。
- **AC2 竄改與損毀偵測**：改掉任何一筆的內容、少掉一筆、最後一筆只寫到一半，讀取時 raise 並指出列號。
  不自動修復：當機寫到一半的檔案由人看過再處理。
- **AC3 時區**：naive datetime 寫不進日誌。
- **AC4 還原等於現場**：在任何時點由日誌還原的部位、均價、已實現損益、成本、當日進場次數、
  停手狀態、當日起始損益、活著的委託，都跟當時運作中的引擎一樣（屬性測試，跨三個交易日）。
- **AC5 接手**：`Engine.restore` 接手還原的狀態並跟券商部位對帳；
  日誌裡有結果不明的委託、券商部位對不上、或引擎已經開始運作，一律拒絕。
- **AC6 停手狀態跨重啟**：緊急停止重啟後、換日後仍然有效，要人工解除；每日虧損造成的停手只在當天有效。
- **AC7 指令列**：`replay --journal <檔案>` 把事件寫進日誌；`verify-journal <檔案>` 驗證雜湊鏈。

### A-004 動能順勢轉接

原版程式（seromitama/Momentum_Scalping，commit 1dea51b）不放進 repo，執行時從資料夾載入。
比對基準是 `reference/day_engine.py`：研究分支 `futures_replay.py` 的 DayEngine 原封不動抽出，
現有模擬單跑的就是它。**基準不可修改。**

- **AC1 逐筆相同**：同一份行情下，autotrade（轉接＋模擬券商＋帳務）的每筆進場時間與價格、出場時間與價格、
  出場原因、淨損益，以及訊號與擋下原因的計數，都跟對照引擎相同；帳上已實現損益等於對照引擎各筆淨損益合計；
  過程中 autotrade 的風控沒有擋單、沒有停手。用假訊號跑 5 個隨機交易日，且假訊號確實走到每一條帳戶規則。
- **AC2 換日**：換日時清掉原版的快取與當日計數；連跑兩天各自等於對照引擎。
- **AC3 退單**：委託被風控擋下、被券商拒絕或被刪單時，策略放掉在途狀態，之後照常評估。
- **AC4 系統強制平倉**：緊急停止把部位平掉後，策略自己記的部位也歸零，該筆記為 `SYSTEM_FLATTEN`。
- **AC5 狀態對不上就停**：策略記的部位跟實際部位不同、收到沒有對應委託的買進成交、沒部位卻收到賣出成交，一律 raise。
- **AC6 時間換算**：時間轉微秒用整數運算，不經過浮點數。
- **AC7 載入原版**：從資料夾找各模組的最新版號並用預設參數；資料夾不存在或缺模組就 raise。
- **AC8 設定**：`[momentum]` 的間隔、預估滑價、口數會驗證；口數不得超過單筆上限。
- **AC9 指令列**：`replay --strategy momentum` 沒給 `--ms-repo` 就報錯。
- **AC10 真實比對（2026-11-12 通過）**：用真的網友原版，在使用者電腦上跑 `tools/parity_momentum.py`，
  至少 5 個有成交的交易日全部一致。
  - 2026-11-13 加了 A-010 之後重跑 11-06、10-29 與新補齊的 11-12，三天仍然一致。
  - 結果：2026-09-09～2026-11-11 共 41 個交易日（40 天各 2 筆成交、10-29 無成交），**41 天全部一致**，
    結束碼 0，autotrade 風控沒有擋單或停手事件。
  - 原版：`C:/t/Momentum_Scalping` commit 1dea51b；設定 `configs/tmf_sim.toml`（未改）。
  - 逐筆：本機 `data/research_ms/taifex_ticks/TMF/Daily_YYYY_MM_DD.csv`（期交所每日逐筆成交，只留微台的列、
    格式不變，可直接餵）。`Daily_2026_11_12.csv` 是當天 08:30 抓的，只有前一晚夜盤，沒有日盤，未納入。
  - 指令：每天一組 `--ticks <檔> --day <日期>`；41 天約 35 分鐘。主控台是 cp950，要設 `PYTHONIOENCODING=utf-8`
    中文才不會變亂碼。

### A-005 把狀態寫給網站

使用者 2026-11-13：「好，先做網站那一頁」。交易程式把「現在怎樣、今天做了什麼」整理成一份狀態，**單向**交給網站；
網站只能看，不能對交易程式下任何指令（緊急停止要在電腦上做）。

資料流：`export.snapshot`（純函數，不寫檔）→ 指令列把它寫成一個 JSON 檔 → `tools/push_status.py` 把那個檔寫進
資料庫 `serving.autotrade_status`（一天、一種模式一列）→ 網站 `/api/autotrade` 讀出來 → 「台指期」分頁的「程式交易」。
只給管理員看（跟小台模擬同一道權限）。

- **AC1 狀態內容**：日期、模式（模擬／真單）、來源（重播／即時）、盤中或已收盤、更新時間、商品、策略；
  現在的部位、均價、最新價、未實現損益、當日已實現損益（含成本）、當日損益、當日成本、進場次數；
  風控上限（口數、進場次數、每日虧損、單一部位停損；沒設就是 null）；商品的每點金額、手續費、期交稅率；
  模擬模式另帶模擬假設（成交延遲、滑價），真單是 null。金額單位是元，時間一律帶 Asia/Taipei 時區。
- **AC2 程式狀態**：四選一——正常、停手、暫停送單、券商連線中斷；停手時帶原因代碼。同時發生時連線中斷優先。
- **AC3 今日成交**：只列這一天的成交（時間、買賣、口數、價格、這筆之後多出來的已實現損益）；
  各筆損益合計等於當日已實現損益。部位被修正過的日子標 `corrected`（逐筆損益只是估算，合計仍以帳為準）。
- **AC4 今日大事**：只留這一天的停手、解除、停損、部位修正、連線、被券商拒絕、不認得的委託、被風控擋下，
  新的在後，最多 `[export] max_events` 則（超過留最新的）；一般的委託與成交不算大事。
- **AC5 沒有行情就不輸出**：還沒收到任何行情時 raise，不輸出一份全是 0 的狀態。
- **AC6 決定性**：同樣的輸入輸出的文字一字不差；可以直接轉成 JSON（中文不轉義）。
- **AC7 設定**：設定檔沒有 `[export]` 時要求輸出就 raise；`max_events` 要大於 0。
- **AC8 指令列**：`replay --status-out <檔>` 在收盤確認後寫出「已收盤」的狀態；先寫暫存檔再改名，
  不會留下寫到一半的檔。資料夾不存在就 raise。
- **AC9 寫進資料庫**：`tools/push_status.py` 的建表語句跟 twquant `AUTOTRADE_STATUS_SPEC` 一字不差（兩邊各有測試守著）；
  同一天同一種模式重寫是覆蓋。狀態檔缺欄位、模式或狀態不認得就 raise，不寫；一次給很多個檔時，
  全部先檢查過、在同一筆交易裡寫完（有一個不合格就一列都不寫）。連線字串只從環境變數讀，
  或用 `--env-file` 從 `.env` 讀同名的那一個變數；不印出來。
- **AC10 網站端點**：`/api/autotrade?mode=sim|live&day=YYYY-MM-DD` 一次回日期清單（新到舊，每天的狀態、當日損益、成交筆數）
  與那一天的整份狀態（沒給 day＝最新一天）；權限在讀資料庫之前擋；表還沒建或沒有紀錄時回空的，不是錯誤。

### A-006 成交與異常通知手機（D-224）

使用者 2026-11-13 選 **Telegram**。資料流：引擎事件 → `notify`（轉成白話、分級、同一件事不洗版；純運算，不連網）
→ `delivery` 的背景佇列 → Telegram 機器人 → 手機。不經過網站，也不 import twquant。
金鑰與收件對象只放環境變數 `AUTOTRADE_TELEGRAM_BOT_TOKEN`、`AUTOTRADE_TELEGRAM_CHAT_ID`（`.env`）。

- **AC1 成交通知**：每筆成交各一則，寫買進或賣出、口數、成交價、成交後帳上的部位。增加部位的成交寫這筆的成本；
  減少部位的成交寫這筆賺或賠幾元（已扣這筆的成本）與當日已實現損益。**回到空手時標題改寫「這一趟」**
  （從進場到出場、成本都扣了）淨賺或淨賠幾元，下一行交代它怎麼由這一筆與前面各筆加起來。
  每筆的金額跟引擎的帳一致，合計等於當日已實現損益；部位沒被修正過的日子，逐筆跟給網站的狀態（A-005 AC3）相同。
  成交不節流、不合併。部位被修正過的那天，成交通知註明損益是估算，也不寫「這一趟」。
- **AC2 異常通知與分級**：停手（含進入暫停送單）、解除、停損、部位修正、券商連線中斷與恢復、被券商拒絕、
  券商端有不認得的委託、被風控擋下、送出刪單、刪單完成各有通知。分三級：
  一般（成交、解除、連線恢復、被風控擋下、刪單完成）、
  注意（程式自己處理完了：當日虧損到上限、停損平倉、新倉單被券商拒絕、委託太久沒成交而刪單、
  斷線前送出的委託沒送到券商、空手且沒有在途委託時斷線）、
  要處理（程式停下來等人，或人要去看部位：緊急停止、部位對不上、暫停送單、不認得的委託、
  有部位或有在途委託時斷線、平倉單被券商拒絕、有部位時平倉方向的單被擋下或送不出去而且沒有別張平倉單在途）。
  「注意」與「要處理」第一行有明顯標記，而且不靜音；
  「要處理」寫出要做什麼，暫停送單與斷線寫出帳上還有沒有部位。
  停手通知依實際的停手狀態寫：暫停送單中按緊急停止，通知會說緊急停止沒有作用；解除後還在停手，通知會說解除沒有生效。
- **AC3 白話**：通知裡不出現內部代碼（停手代碼、`BUY`／`SELL`、事件種類）。停手代碼的對照表涵蓋風控的每一個代碼；
  引擎會寫出的每一種事件 `notify` 都認得（靜態檢查：引擎多了新事件而通知不認得，測試會紅）。
  遇到不認得的代碼不吞掉，照樣寫出來並標明是代碼。
- **AC4 同一件事不洗版**：同一個原因被擋下（例如斷線期間策略一直想送單），`throttle_s` 內只即時通知第一則；
  其他種類同一類在 `throttle_s` 內最多即時送 `burst` 則。超過的不丟掉，合併成一則（帶次數、起訖時間、合併了哪些事、
  最後一則的內容），在視窗空出來時送出（`poll` 或結束時）；用掉最後一個即時名額的那一則會預告接下來要合併。
  合併的那一則標題會標出次數，等級取其中最嚴重的。
  **「要處理」的通知不受這個上限限制**（重複被擋下的那一類除外）：一定當下就送，送之前先把同一類壓著的合併送出，順序不顛倒。
  不變量：任一 `throttle_s` 視窗內同一類送出的則數不超過上限，而且送出的通知涵蓋的事件數等於發生的事件數（屬性測試）。
- **AC5 送失敗不影響交易**：送出在背景做，引擎那邊只把通知放進佇列，不等網路。送的動作卡住、一直失敗、丟出沒預期的錯誤，
  或通知內容產生失敗時，引擎照常處理行情與成交，事件與損益跟沒開通知時完全相同。
- **AC6 失敗留紀錄**：通知嚴格照順序送，前一則還沒有結果，後面的不會先送（網路恢復後收到的順序才不會亂）。
  連不上、逾時、對方要我們慢一點，就每隔 `retry_wait_s`（或對方要求的秒數）再試，一直試到送出去或程式結束；
  連續失敗 `warn_after_attempts` 次時留一筆紀錄（標明還在重試，每則只記一次）。再試也不會成功的錯誤（金鑰或收件對象不對）不重試。
  沒送出去的——不重試的、佇列滿了被丟掉的、結束時還沒送出或還在送的、內容產生失敗的——每一則都留一筆紀錄
  （事件時間、哪一則、原因、試了幾次）。之後第一則送成功的通知會註明前面有幾則沒送出去，而且不靜音。
  送出的則數＋沒送出的則數＝交給佇列的則數（屬性測試）。
- **AC7 送出介面與 Telegram**：`Sender` 是可替換的介面；真的送的是 `TelegramSender`，測試與預覽用 `MemorySender`
  （記在記憶體）與 `PrintSender`（印在畫面上）。`TelegramSender` 的請求內容（網址、收件對象、文字、靜音旗標、太長就截斷）
  與錯誤對應（連不上、逾時、429 與 5xx 可以重試；其他 4xx 不重試並附白話提示；回應讀不懂）用假的連線測。
  **測試不連網**：測試期間任何連線嘗試都會 raise。
- **AC8 設定**：`[notify]` 的管道、商品稱呼、要通知的種類、一般通知要不要靜音、節流、重試、佇列大小、結束時等多久都會驗證；
  不認得或重複的種類、不合理的數值（零或負數、不是有限的數字、該是整數卻不是）就 raise；重試的間隔不能是 0。**真單模式一定要有 `[notify]`，而且要包含成交與所有會標「注意／要處理」的種類**
  （成交、停手、停損、部位修正、連線、被券商拒絕、不認得的委託）。
- **AC9 金鑰不外洩**：金鑰與收件對象只從環境變數讀（或 `--env-file` 指的 `.env` 裡同名的變數）；缺了就 raise，
  訊息只寫變數名稱。錯誤訊息、失敗紀錄、畫面輸出裡都不出現金鑰與收件對象（底層錯誤帶著網址時會被遮掉）。
- **AC10 指令列**：`notify-test` 送一則測試通知（由使用者執行），失敗時結束碼不是 0 並寫出原因；
  `notify-setup` 請機器人在 Telegram 裡回覆每個跟它說過話的人自己的收件代號（不印在電腦畫面上）；
  `replay --notify print` 把那一天的通知印在畫面上（不連網），`--notify send` 真的送；
  `--notify-log <檔>` 把沒送出去的通知記進檔案。重播結束時印出送出與沒送出的則數。
- **AC11 決定性**：同樣的事件輸出的通知一字不差（含合併的那一則）。
- **AC12 重啟後接手**：從日誌還原狀態重啟時，通知用的小帳接手還原的部位、均價與當日損益，之後的成交損益照樣算得對
  （重啟前的進場不在這次的事件裡，那一趟只寫這一筆，不寫「這一趟」）。
- **AC13 時區**：通知上的時間一律是 Asia/Taipei。事件時間沒有時區就不當成台北時間送出去：記成內容產生失敗，改送替代通知。

**第二管道：網站 App 的推播（D-224 修訂，使用者 2026-11-13：「加第二管道」）**。Telegram 照舊收全部；

- **AC14 分級**：只有等級達到 `min_level` 的通知進推播；Telegram 不受影響、照樣收全部。兩邊各自計數與留紀錄。
- **AC15 每台裝置各自一條佇列**：一台裝置送不出去或卡住，不影響另一台，也不影響 Telegram，引擎照常。
- **AC16 推播內容**：標題＝通知第一行，內文＝其餘各行，點了開 `[notify_push] url`；每則有自己的 tag（不會互相蓋掉）；
  帶「高優先」標頭與 `ttl_s`。用網站同一把 VAPID 私密金鑰（環境變數 `TWQUANT_VAPID_PRIVATE_KEY`）簽章。
- **AC17 推播服務的回應**：2xx 算送到；404／410＝這台裝置的通知已失效，不重試，紀錄寫「請在網站重新開通知、重新拉訂閱」；
  429、5xx、連不上可以重試。錯誤訊息只寫推播服務的主機名稱，不寫訂閱網址與金鑰。
- **AC18 訂閱檔**：只收 https、`allowed_hosts` 裡的推播服務，欄位缺了就 raise；一台都沒有就 raise（不默默只剩 Telegram）。
  拉訂閱的工具只拉 `AUTOTRADE_PUSH_EMAIL`（`.env`）那個帳號的，只讀資料庫，畫面只印台數。
- **AC19 設定**：`[notify_push]` 的等級、網址、存活時間、逾時、推播服務清單、聯絡網址都會驗證；沒有這一段就沒有第二管道。
- **AC20 指令列**：`notify-test --channel push --push-subs <檔>` 對每台裝置送一則測試推播；
  `replay --notify send --push-subs <檔>` 兩個管道一起送，結束時分別印出送出與沒送出的則數。

### A-015 遠端緊急停止的「門鈴」：按下去就推到本機（D-228）

使用者 2026-11-14：「緊急停止可以透過 mq 來發送接收嗎，在手機發送停止到後端，後端發 MQ，本機後台收到停止 cli」→「好，做 MQ 停止」。
A-011 靠輪詢：中繼程式每 `poll_s`（2 秒）問一次資料庫、交易程式每 `poll_s` 讀一次指令檔，最慢約 4 秒才停。
這一輪加一個門鈴：資料庫一有新的停止指令就通知中繼程式，中繼程式馬上去拿，交易程式看到指令檔換新也馬上讀。
推播用的是資料庫內建的 `LISTEN`／`NOTIFY`（為什麼不另外租 MQ、實測的數字，見 D-228）。**輪詢原封不動留著當備援。**

```bash
python tools/run.py relay --config configs/tmf_sim.toml --dir <資料夾> --consumer sim --dsn-env TWQUANT_SUPABASE_DSN --env-file D:/project/twquant/.env --bell --bell-port 5432
python tools/run.py admin … --bell-port TWQUANT_SUPABASE_DSN=5432     # 後台啟動的指令中繼會自己帶 --bell
```

- **AC1 資料庫端**（`relay.BELL_DDL`）：指令表每新增一列，資料庫自己發一則通知（頻道 `autotrade_ring`，內容只有表名與編號）。
  函式與觸發器由中繼程式帶 `--bell` 啟動時建（跟建表一起、建好一次就不再建，可以重複執行）。不帶 `--bell` 時不建。
  A-011 的八句建表語句不動；網站的程式不用改（Hyperdrive 不支援 `NOTIFY`，所以不由網站那一句 SQL 發）。
- **AC2 聽門鈴**（`bell.PgBell`）：另一條資料庫連線、自己一條背景執行緒。聽到 `autotrade_ring` → `wait()` 馬上回 True；
  沒聽到 → 等滿給的秒數回 False。通知的內容不當指令用：要停什麼，一律回資料庫查（A-011 的查詢）。
- **AC3 自己測**：連上之後、以及之後每 `check_s` 秒，**由另一條連線**在自己專用的頻道按一次測試鈴，`heard_within_s` 秒內聽到才算「聽得到」。
  聽不到（例如連到交易模式的連線池）→ 狀態變「聽不到」、關掉重連，間隔從 `retry_s` 起每次加倍、最多 `retry_max_s`；確認聽得到之後歸零。
  別支程式的測試鈴、過期的測試鈴都不算。聽的那條連線除了 `LISTEN` 什麼都不送：在它自己身上按，就算平常聽不到別人，
  也會在自己那一句的回應裡收到，測不出來（雲端實測抓到的）。按測試鈴的那條連線走連線字串原本的埠，跟網站寫入指令走的路一樣。
- **AC4 只會變快、不會變慢**：連不上、斷線、聽不到、甚至沒料到的錯誤，都不丟到中繼程式的主迴圈；`wait()` 最長就是等滿給的秒數。
  門鈴整個壞掉時，中繼程式的行為跟 A-011 一樣（每 `poll_s` 一輪）。
- **AC5 中繼程式的迴圈**（`relay.run`）：有門鈴時用 `bell.wait(poll_s)` 取代睡覺，被叫醒就馬上跑一輪並印一行；
  門鈴「聽得到 ↔ 聽不到」改變時各印一行（聽不到時寫原因，並講明照舊每幾秒問一次）。沒給門鈴時跟 A-011 一模一樣。
- **AC6 交易程式那一端**：指令檔在上次讀過之後換新了（`FileControl.changed`，只看檔案時間），`ControlLoop.step` 就不等自己的 `poll_s`、馬上讀。
  還是只碰本機檔案。沒有接這個檢查的 `ControlLoop` 行為不變。模擬交易程式（A-014）與演練（A-011）都接上。
- **AC7 整條路不等輪詢**：門鈴響 → 中繼程式馬上跑一輪 → 指令檔換新 → 交易程式下一圈就讀到、停手——中間沒有任何一段在等 `poll_s`。
- **AC8 指令與後台**：`relay --bell`（開門鈴）、`--bell-port N`（聽的時候改連這個埠；只給 `--bell-port` 沒給 `--bell` 會被拒絕）；`--once` 不開門鈴。
  後台 `admin --bell-port 環境變數名=埠`（可以給好幾個），它啟動的指令中繼（交易程式、演練）一律帶 `--bell`，選到的資料庫有對應的埠就帶 `--bell-port`。

### A-011 遠端緊急停止（D-225）

使用者 2026-11-13：「我緊急停止要遠端可以操作阿」。網站可以要求交易程式緊急停止；**只能叫停**，不能解除、不能開始、不能改設定。
第一版設計寫完後請三位獨立審查者挑毛病（安全、交易風險、實際運作），12 項意見經反方查證全數成立，下面是改過之後的設計。

資料流（交易程式自己**不連資料庫**）：

```
網站「緊急停止」 → PUT /api/autotrade/stop → web.autotrade_commands 多一列
   → 中繼程式（另一支程序，relay.py）每 poll_s 秒讀一次 → 寫成本機的指令檔 commands.json
   → 交易程式的 ControlLoop 讀指令檔 → Engine.on_control 停手、平倉 → 結果接在本機的回報檔 results_<日>.jsonl 後面
   → 中繼程式把結果送回 web.autotrade_command_acks（一支程式一列），並在 web.autotrade_listeners 留心跳
   → 網站每支程式一行：在不在聽、收到了沒、最後平掉了沒
```

交易程式這一側（`engine`、`control`）：

- **AC1 只認得停止、只管今天、一筆只做一次**：指令只有 `stop`；不是今天（台北日期）的、動作不認得的，不執行，記一筆事件並回報原因。
  處理過的指令用「編號＋按下的時間」認，只記當天、隔天清掉——不用「編號比上次大」：指令表重建、編號重來也不會漏。
- **AC2 停止怎麼做**：等同在電腦上按緊急停止（`Engine.kill`，兩者同一條路）。連線通的時候**先問券商實際的部位**再平——
  停止可能晚到，人可能已經用券商的 App 平掉了，照帳上的數字再賣會變成放空；券商已經是 0 就只停手、不送單。
  日誌**先記停手、再記這筆指令處理過了**：中間當機，重啟後是「還沒處理（會再做一次）」，不會是「處理了卻沒停」。
  回報的文字照當下的狀態寫，並帶按下與執行的時間（晚了多久看得出來）。
- **AC3 重啟**：只還原今天處理過的指令。停著的時候重啟：不重做，但結果再報一次（當機前可能來不及報）。
  在電腦前解除之後重啟：同一天的舊指令不會再把它停一次。昨天的不帶過來。
- **AC4 只能叫停**：這條路沒有任何解除或開始交易的動作。不變量（屬性測試）：對任意的指令序列，套用之前是停手的，套用之後一定還是停手；
  「暫停送單」不會被降級。`control.py`、`relay.py` 的原始碼不碰解除。
- **AC5 追蹤到確認平掉**：一筆停止回報兩個階段。先是 ack（收到了、當下怎麼處理：`flat`／`cancelling`／`flattening`／`link_down`／`suspended`／`ignored`），
  之後是 done：連線通、沒有部位、沒有委託 → `flat`；程式在暫停送單、或過了 `flatten_timeout_s` 還沒平掉 → `stuck`（要人處理，只講一次）；
  之後平掉了再報 `flat`；在電腦前解除 → `released`。券商連線中斷時帳上是空的也不算 `flat`，要等連線恢復對過帳。
- **AC6 不靠行情也做得完**：斷線中收到停止 → 連線一恢復就平倉，不等下一筆行情。`Engine.on_timer` 用時鐘叫：停手中或過了強制平倉時間就平倉（不做逾時刪單：委託的時間是行情的時間，跟電腦的時鐘差幾秒就會誤刪剛送出的委託）。
- **AC7 讀不到指令不影響交易**：指令來源出錯時引擎的部位、委託、停手狀態都不變；只在「變成讀不到」與「恢復」各記一次事件。
  讀不到新指令時，仍然繼續追蹤先前的停止有沒有平掉。結果記不下來會留著重試，不會丟。輪詢用時鐘，不靠行情。
- **AC8 交易程式這一側只碰本機檔案**：`FileControl` 只讀指令檔、只往回報檔後面接、每次讀就留下心跳。指令檔不存在、超過 `stale_s` 沒更新、

- **AC9 狀態看得到**：快照多一塊 `control`（有沒有在聽、上一次成功讀到的時間、現在讀不讀得到、多久讀一次、今天處理到第幾號）。
  「遠端連線通／不通」的事件再多，也不會把停手這類事件擠出「今日大事」。
- **AC10 設定**：`[control]` 的 `poll_s`、`flatten_timeout_s` 要大於 0，`stale_s` 至少是 `poll_s` 的兩倍。沒有這個區塊＝不聽遠端指令；
  **真單模式沒有這個區塊就拒絕啟動**。

  ack 一支程式對一筆指令只留第一次，done 後寫的蓋掉先寫的；時間都用資料庫的時鐘。中繼程式不新增、不刪、不改指令。
- **AC12 跑一輪**：先把回報檔裡還沒送的結果照順序送回去，再拿指令寫成指令檔（先寫暫存檔再改名）。送過的不重送；寫到一半的那一行等下一輪；

  `Runner.run` 外面。模擬券商不會出錯所以碰不到；接元大後要接住、記下來、下一輪再查（A-011 第二輪審查留下的）。
- 引擎自己送的平倉單（緊急停止、強制平倉）記的是電腦的時間，逾時刪單比的是行情的時間：電腦的時鐘比行情慢超過
  `order_timeout_s` 時，還沒成交的平倉單會被下一筆行情當成逾時、刪掉重送。模擬券商下一筆行情就成交所以碰不到；
  接元大時這類單要用同一種時間算逾時（A-011 第二輪審查留下的）。

手機通知（A-006）。設定步驟在 `README.md`；金鑰與收件代號放 `.env`，指令用 `--env-file` 去讀：

```bash
python tools/run.py notify-setup --config configs/tmf_sim.toml --env-file D:/project/twquant/.env
```

```bash
python tools/run.py notify-test --config configs/tmf_sim.toml --env-file D:/project/twquant/.env
```

`tools/run.py` 跟 `python -m autotrade` 是同一支指令列，只是不用先設 `PYTHONPATH`（PowerShell、cmd、bash 都是同一行）。
`notify-test` 加 `--level warn` 或 `--level act` 可以看「注意」「要處理」長什麼樣（會響）。
`replay` 加 `--notify print` 把那一天會發的通知印在畫面上（不連網）；`--notify send` 真的送到手機（標「重播」）；
`--notify-log <絕對路徑>` 把沒送出去的通知記進檔案。會連到 Telegram 的指令（`notify-setup`、`notify-test`、`--notify send`）由使用者自己執行。
